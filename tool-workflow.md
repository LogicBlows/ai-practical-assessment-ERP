# Tool Workflow

## Primary AI Tool Used
Cursor, used as an agentic pair-programming tool throughout the entire
build — from initial solution scaffolding through to final testing and
documentation generation.

## How I Provide Project Context to the Tool
Context was established upfront rather than re-explained in every
prompt. The very first prompt to Cursor laid out the full architectural
constraints as fixed rules: Clean Architecture layering (Domain/
Application/Infrastructure/Shared/Web), no business logic in
controllers or views, no direct DbContext access outside Infrastructure,
a ServiceResult<T> pattern for service responses, and the multi-tenant
CompanyId convention. Every subsequent prompt built on this shared
foundation rather than repeating it, which kept generated code
consistent across nearly 20 feature prompts. For documentation
generation later in the project, Cursor was given direct access to the
existing codebase and asked to draft content grounded in what was
actually implemented, rather than working from a description alone.

## Requirement Analysis and Planning/Design
Requirements were interpreted from the assessment brief first, then
translated into concrete technical decisions before any prompting began
— for example, deciding to seed two companies (Sharma Trading Co. and
Verma Distributors) specifically to make multi-tenant isolation
demonstrable, not just declared. Planning happened prompt-by-prompt: each
feature was scoped into its own focused prompt (entities, then DbContext,
then seed data, then auth, then each business feature in turn) rather
than requesting the whole application at once, which kept each step
reviewable and made debugging tractable when something went wrong.

## Code Generation
Code was generated feature-by-feature on dedicated Git branches, each
merged via its own pull request only after manual verification. Prompts
were deliberately scoped narrowly (e.g. "seed data only, no auth yet";
"list and search only, no create forms yet") to keep each generation
reviewable rather than accepting large, multi-concern changes at once.

## Validation
Every feature was manually tested in the running application before
being considered complete — not just checked for a successful build.
This included logging in as both seeded tenant accounts to confirm data
isolation, hand-calculating quotation totals against the app's output
to verify tax/discount logic, and directly querying the database in SQL
Server Management Studio to confirm seed data and migrations actually
produced the expected rows, rather than trusting console output alone.

## Testing
The two mandatory xUnit tests (quotation calculation, settings
defaults) were generated via Cursor but built around concrete,
hand-verified figures from real manual testing, so the tests would
catch an actual regression rather than just re-confirm arbitrary
values. `dotnet test` was run directly to confirm pass/fail rather than
trusting the generation summary.

## Debugging
Six real issues were found and fixed during development, all logged in
debugging-notes.md: a stale process holding a port and later a locked
DLL; a font rendering bug in generated PDFs; a recurring EF Core
DbContext concurrency bug (Task.WhenAll used against a shared, non-
thread-safe DbContext) that appeared independently in two separate
features; and a missing DI service registration that silently broke an
entire controller. Each was found through direct inspection — reading
actual error stack traces, checking the database directly, or visually
reviewing generated output — rather than assuming a bug didn't exist
because the build succeeded.

## Code Review
After each feature was generated, the diff was reviewed against the
project's architectural rules (no DbContext in controllers, correct
layering) and cross-checked against manual testing results before
committing. Several instances were caught where Cursor under-delivered
on a multi-part prompt (e.g. seeding only one of four requested entity
types) — caught specifically by checking the database directly rather
than trusting a stated summary.

## What I Avoid Sharing Unnecessarily with AI Tools
No real credentials, connection strings with actual passwords, or
production data were ever shared with or generated by the tool — all
seeded data is fictional, and the JWT signing key is generated at
runtime and stored only in the database, never in source or prompts.

## How I Would Reuse This Workflow in a Real Project
The core habits — scoping prompts to one reviewable concern at a time,
establishing architectural constraints once upfront rather than
repeating them, and verifying every feature manually before considering
it complete rather than trusting a successful build — transfer directly
to real project work. The discipline of catching AI under-delivery by
checking actual system state (database contents, running application
behavior) rather than AI-reported summaries is, if anything, more
important in a real production codebase than in this exercise.
